# D-ASR-002 刷新后网页与后端协同

## 背景与目标

| 字段 | 说明 |
|---|---|
| 要解决的问题 | 刷新清掉页面上的文件、结果和日志，服务端转写仍占着单飞锁，再提交要么没反应要么 429 |
| 业务/技术背景 | 浏览器不能在刷新后保留未提交的文件。转写进度只推给当时的连接 |
| 目标边界 | 刷新后能看出转写是否还在跑，并补上近期日志。不恢复文件，不中断正在跑的推理 |

## 架构设计

### 用法与接口

```text
打开页面
 → GET /health  增加 busy
 → GET /api/events  先回放近期日志，再推 {log, busy}

无文件就提交 → 页面写「请先拖入」，不发请求
正在转写 → 按钮禁用
转写结束 → 推 busy=false，按钮恢复
刷新 → 再走一遍打开页面
客户端断开 → 转写继续，锁在结束后释放
```

`GET /health` 在原字段上增加 `busy`。日志事件为 `{"log": "...", "busy": true|false}`。只表示空闲时可以只有 `busy`。

### 核心思路

**页面状态以服务端为准，文件只活在这一次页面。** 刷新不是新的一次转写，只是重新订阅。

### 协同

```text
L1 页面
  health.busy → 禁用提交
  events 回放 + 增量 → 日志区，并按 busy 开关按钮
       ▼
L1 HTTP
  health 读 L2 是否占锁
  events 订阅时在同一把锁里取近期日志，避免漏一条或重一条
       ▼
L2 单飞
  占锁期间 busy=true
  跑完释放锁，再推 busy=false
```

### 关键设计点

| 设计点 | 是什么 | 为什么这么定 |
|---|---|---|
| busy | health 与日志事件上的同一个字段 | 刷新先看锁，随后靠事件解锁 |
| 日志回放 | 订阅时拷贝近期记录 | 刷新后的页面能接上进度 |
| 不恢复文件 | 刷新后要重新拖入 | 浏览器不保留未提交文件 |
| 断开不取消 | 推理继续占锁 | 中途杀推理不能安全释放模型 |
| 中途正文 | 一次生成里，解出正文标记之后的字就推到结果区 | 官方按音频切片推送要显卡，这台机器做不到 |

## 被排除方案

| 方案 | 排除原因 |
|---|---|
| 把上传文件存下来供刷新重放 | 刷新不是重做同一请求 |
| 断开就中断模型生成 | 释放不干净，下一次冷启动更乱 |
| 只靠页面内存里的 busy | 刷新后丢失，正是这次要修的 |

## 不变量与约束

| 类型 | 内容 |
|---|---|
| 不变量 | 同一时刻最多一个转写 |
| 不变量 | 一条日志要么在回放里，要么在之后的推送里 |
| 约束 | 无文件不发请求 |
| 约束 | 占锁期间新的提交仍是 429 |
